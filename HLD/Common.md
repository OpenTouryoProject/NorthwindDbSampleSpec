## 1. 本書の位置付けと前提

| 項目 | 内容 |
| :--- | :--- |
| 対象システム | NorthwindDb を用いたサンプル業務アプリケーション |
| 対象 DB | Microsoft SQL Server サンプル DB「Northwind」（[原典](https://github.com/microsoft/sql-server-samples/tree/master/samples/databases/northwind-pubs)） |
| アプリ形態 | Web アプリケーション（マルチユーザ、ブラウザからの利用） |
| 技術スタック | **特定のフレームワークに依存しない**。本設計書はコントロール名・API 名・ライフサイクル名を用いず、「一覧表」「ドロップダウン」「ページ読み込み」等の一般語で記述する |
| 文字コード | UTF-8 / 日本語表示。DB 側は Northwind 原典どおり Unicode 型（`nvarchar` 等） |

### 設計スコープ（作らないもの）

本システムはサンプルであり、次の設計・実装は**行わない**。設計書中にこれらを登場させてはならない。

- ワークテーブル、採番テーブル（採番は `IDENTITY` を用いる）
- 変更履歴テーブル、監査ログテーブル
- 論理削除（削除は物理削除とする）
- 非同期処理（帳票・印刷を含む）、ジョブ、キュー
- データ・キャッシュ層
- ドメイン駆動設計（DDD）に基づく戦術的パターン（エンティティ／値オブジェクト／リポジトリ等の設計）

帳票は**同期処理**とし、ブラウザの印刷機能を用いる印刷用画面として設計する。

### 金額の算出式

設計書中の金額項目は、次の式で統一する。

| 名称 | 式 |
| :--- | :--- |
| 明細単価（割引後） | `Order Details.UnitPrice × (1 - Order Details.Discount)` |
| 明細金額 | `明細単価（割引後） × Order Details.Quantity` |
| 小計 | `Σ 明細金額`（同一受注の全明細） |
| 受注合計 | `小計 + Orders.Freight` |

- 割引率 `Discount` は 0〜1 の実数（0.15 は 15% 引き）。
- **計算は 10 進数型で行い、浮動小数点型で行わない。** `Discount` は DB 上 `real`（単精度）であり、
  そのまま計算すると誤差が蓄積する（[テーブル定義書の「`Discount` の扱い」](../LLD/TableSchema.md#discountrealの扱い--実装時の注意)）。
- 明細金額は小数第 3 位を四捨五入して小数第 2 位までとし、その値を合算して小計とする。
- 画面表示は通貨記号なしの千区切り＋小数 2 桁とする。

## 6. 共通検証ルール

ID の書式は `VAL-<名称>`。

| ID | 検証内容 | エラー時の扱い |
| :--- | :--- | :--- |
| `VAL-REQUIRED` | 必須項目が未入力でないこと | `ERR-VALIDATION` |
| `VAL-LENGTH` | 文字列項目がテーブル定義書の桁数以内であること | `ERR-VALIDATION` |
| `VAL-NUMERIC` | 数値項目が数値として解釈でき、定義された範囲内であること（数量 > 0、単価 >= 0、割引 0〜1、在庫数・発注済数・発注点 >= 0、対象年 >= 1900、対象月 1〜12、目標金額 >= 0） | `ERR-VALIDATION` |
| `VAL-DATE` | 日付項目が日付として解釈でき、日付の前後関係が矛盾しないこと（受注日 <= 要求納期、受注日 <= 出荷日） | `ERR-VALIDATION` |
| `VAL-CODE` | コード項目が定められた書式であること（顧客 ID は英大文字 5 桁） | `ERR-VALIDATION` |
| `VAL-EXISTS` | 選択・入力された外部キーの値がマスタに存在すること | `ERR-VALIDATION` |
| `VAL-DUP` | 一意であるべきキーが既存データと重複しないこと | `ERR-VALIDATION` |

検証は**保存操作の前に全項目をまとめて実施**し、エラーがある場合は 1 件も更新せずに全エラーを表示する。

> **DB は妥当性を保証しない。**
> 業務系で使用しない制約（外部キー・CASCADE・CHECK・UNIQUE・トリガー）は DB に定義せず、
> アプリケーションで担保する方針である（[DB に持たせない制約](../LLD/TableSchema.md#db-に持たせない制約)）。
> DB が弾いてくれることを前提にせず、**本節の検証を必ずアプリ側で実施すること**。
> とくに `VAL-EXISTS`（参照先の存在確認）と `VAL-DUP`（重複確認）は、
> 従来 DB の外部キー制約・一意制約が担っていた役割を代替するものであり、省略できない。

## 7. 共通エラーハンドリング

ID の書式は `ERR-<名称>`。

| ID | 発生条件 | 動作 |
| :--- | :--- | :--- |
| `ERR-DB` | データベースへの接続・実行に失敗した | 「データベースに接続できませんでした。時間をおいて再試行してください。」を表示し、画面の状態は変更しない |
| `ERR-NOTFOUND` | 指定されたキーのデータが存在しない（他ユーザによる削除を含む） | 「対象のデータは存在しません。」を表示し、当該モジュールの一覧画面へ戻る |
| `ERR-VALIDATION` | 6 節の検証に違反した | 該当項目にエラー内容を表示し、入力値を保持したまま画面に留まる。更新は行わない |
| `ERR-CONFLICT` | 更新対象の行バージョンが読み込み時と異なる（9 節） | 「他の利用者によって更新されています。最新の内容を読み込み直してください。」を表示し、更新を取り消して最新データを再表示する |
| `ERR-FK` | 他テーブルから参照されているデータを削除しようとした | 「他のデータから参照されているため削除できません。」を表示し、削除を行わない |
| `ERR-BIZ` | 業務ルールに違反した（個別のイベント仕様で定義） | 違反内容に応じたメッセージを表示し、処理を行わない |

- 更新を伴う処理は 1 トランザクションで実行し、いずれかのエラーが発生した場合はロールバックする。
- 上記いずれにも当てはまらない例外は `ERR-DB` と同じ扱いとする。

## 9. Northwind 原典への追加

`AGENTS.md` の方針に従い、Web アプリケーションとして必要な最小限の追加のみを行う。追加した要素はテーブル定義書の備考欄に「追加」と明記する。

### 9.1 楽観排他用の行バージョン列（`RowVersion`）

複数利用者が同一データを同時に更新した際の上書き事故（ロストアップデート）を防ぐため、
**更新対象となるテーブル**に行バージョン列を追加する。

#### 定義

| 項目 | 内容 |
| :--- | :--- |
| 列定義 | `RowVersion int NOT NULL DEFAULT 1` |
| 追加対象 | `Orders`, `Order Details`, `Customers`, `Products`, `Categories`, `Suppliers`, `Employees`, `Shippers`, `SalesTargets`（9 テーブル） |
| 追加しない | `Region`, `Territories`, `EmployeeTerritories`, `CustomerDemographics`, `CustomerCustomerDemo`（参照または関連の付け外しのみで、行の項目更新を行わないため） |
| 採番 | **アプリケーションが更新のたびに +1 する**。DB は自動更新しない |
| 画面表示 | しない（画面定義書の画面項目には含めない） |

#### 制御方式

1. 画面表示時に読み込んだ `RowVersion` を画面が保持する。
2. 更新・削除の `WHERE` 句に、主キーとあわせて保持していた `RowVersion` を指定する。
3. **更新時は `SET` 句で `RowVersion` を +1 する。**
4. 更新・削除の件数が 0 件のときは `ERR-CONFLICT` とする。
   （主キーの行自体が存在しない場合は `ERR-NOTFOUND`。両者を区別すること）

**更新の定型文。すべての更新系イベントはこの形に従う。**

```sql
UPDATE   <テーブル>
   SET   <更新する列> = <値>
       , RowVersion = RowVersion + 1        -- ★ 必ず書く
 WHERE   <主キー>   = <値>
   AND   RowVersion = <画面が保持していた値>
```

削除の定型文。削除では `RowVersion` を更新しない。

```sql
DELETE FROM <テーブル>
 WHERE <主キー> = <値> AND RowVersion = <画面が保持していた値>
```

登録時は `RowVersion` を列に含めない（`DEFAULT` により 1 で初期化される）。

> **`RowVersion = RowVersion + 1` の記述漏れは、競合検知を無言で無効化する。**
> 加算を忘れると版数が進まないため、後続の更新が古い版数のまま通り、
> 先行更新が上書きされる（ロストアップデート）。
> [トリガーを使わない方針](../LLD/TableSchema.md#db-に持たせない制約)のため DB 側では救えない。
> 更新系イベントを実装する際は、必ず上記の定型文から書き始めること。

#### 方式の選定理由

行バージョンの実現方式には複数の選択肢があるが、**整数の版数をアプリが +1 する方式**を採用する。

| 方式 | 採否 | 理由 |
| :--- | :--- | :--- |
| **整数の版数列（採用）** | ○ | 全 DB で同一に動作する。精度差・時刻同期の問題が原理的に発生しない |
| DB 固有の行バージョン機構 | × | SQL Server の `rowversion` は理想的だが、他 DB に同等物がない。Oracle の `ORA_ROWSCN` は `ROWDEPENDENCIES` なしではブロック単位、PostgreSQL の `xmin` は `VACUUM FREEZE` で変化、MySQL の `TIMESTAMP` は既定の秒精度では同一秒内の更新を検知できない |
| GUID | × | 一意性は得られるが、順序を持たず、整数より記憶域と比較コストが大きい |
| UNIX 時間・タイムスタンプ | × | **DB 間で時刻の精度が異なり、時刻同期のリスクも排除できない**。同一時刻内の更新を取りこぼす |

特別の事情がない限り、DB 間での精度差や時刻同期リスクを完全に排除できる**版数（整数 +1）方式**が最も安全である。
この方式は[クロス DB 対応](../Northwind/SQLSvr/README.md)（SQL Server / Oracle / PostgreSQL / MySQL）を前提とした選定であり、
制約をアプリで管理する本システムの方針とも一致する。

### 9.2 売上目標テーブル（`SalesTargets`）

- パフォーマンス分析の「目標設定・進捗トラッキング」要件は Northwind 原典のテーブルだけでは満たせないため、担当者別・年月別の売上目標を保持するテーブルを 1 つ追加する。
- 詳細は [テーブル定義書（パフォーマンス分析）](../LLD/TableSchema/Analysis.md) を参照。
